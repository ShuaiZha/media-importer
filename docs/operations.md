# 使用与维护

下文的容器命令用于 Docker 部署。原生 CLI 使用 `media-importer status`、`start`、`stop`、`check`、`logs`、`update` 和 `uninstall`；普通卸载保留数据，`uninstall --purge` 删除本机登记的数据，具体见[原生部署说明](native.md)。日常同步和原片处理继续通过飞书操作；停止后台服务与关闭同步是不同操作。

## 日常使用

1. 用 USB 数据线连接已开机的相机，确保 T7、Docker 和 SMB 网络可用。
2. 收到飞书相机确认卡后核对型号和序列号，点击「确认并备份」。导入与上传并行，第一个文件完整缓存后即可上传。
3. 按状态卡中的连接要求断开相机；原片清理尚在进行时保持连接。电脑和缓存盘需保持可用，直到上传结束。
4. 「同步 → 停止同步」同时停止两路和原片删除，完整缓存保留，中断文件下次从头传输。

「原片处理」保留导入后删除开关，开启需要确认。其他设置在 [`config/settings.json`](../config/settings.example.json) 中维护，字段说明见[部署配置](deployment.md#配置与数据)。`.env` 保存连接、挂载与凭据。

状态卡只展示当前任务、两路进度、相机连接要求、待处理原因和归档位置。上传达到 100% 后仍须确认正式归档；缓存清理失败不减少已归档数量。通知开启时，进度更新原卡，完成和失败单独提醒。诊断、自检和缓存核验使用本机维护命令，不再占用机器人菜单。

素材范围由 `backup.media_scope` 设置为 `all` / `video` / `photo`；照片包含 RAW，完整缓存始终继续上传。`backup.archive_previews` 默认 `false`，仅忽略确认关联的 LRV、THM，未知或孤立文件保留。既有任务按登记时规则处理；未选类别原片不删除。

普通重启保留开关，但当前相机需要重新确认；未确认时完整缓存仍可继续上传。需要防止电脑睡眠时，macOS 可在传输期间运行 `caffeinate -i`；电脑、Docker 和网络需保持可用。

### 一次一清

SQLite 保存未完成事项及必要的去重、投递信息。整轮正式归档成功、完整缓存已清理、所选原片清理已完成后，自动删除任务明细和批次记录。失败或清理不确定时保留记录。

原片选择保留时留下最小去重索引；完整扫描确认原片已不在卡上后清除，断开相机不会清除。同名新素材仍按身份区分，并使用重名后缀。之后开启原片删除时，先核验既有归档身份，不重复上传。

完成通知保存独立摘要，失败重试，成功后删除投递事项；飞书中已收到的消息仍可阅读。状态菜单只查看当前任务，收尾后显示待机。少量消息去重 ID 保留一天，避免延迟回调重复执行；保留一个归档文件身份作为修改 SMB 连接时的核验依据。

升级前备份数据目录及完整缓存。升级保留配置、未完成任务、完整缓存和归档路径，自动收尾已完成且无待处理事项的旧明细，不补发历史完成提醒。既有 SMB 文件不移动、不删除。旧的只读菜单返回综合状态，旧修改卡片停用；按飞书指南精简后台菜单并发布。

## 传输与清理规则

导入先写本地临时文件；下载完整后核对大小和源身份，落盘、改名为完整缓存、保存记录。只有完整缓存进入上传队列。

上传使用唯一隐藏临时文件，写完核对大小与身份，以禁止覆盖方式改为正式名称，保存归档记录后清理对应缓存。正式目录为：

```text
目标子目录/设备名-序列号/原文件名
```

所有日期和 DCIM 子目录的素材在设备目录内平铺。不同素材同名或大小写冲突时添加 `_1`、`_2` 等后缀。已分配路径持久化。改名响应丢失时用操作记录和文件身份核验，不能仅凭同名同大小认领文件。不全量读回视频，不计算视频 SHA-256。

**不保留字节断点。** 停止、断网或重启后，未完成文件从零重传。已完整导入和已正式归档的文件不会重传。只删除确认归属的半文件；离线时登记待清理，恢复后处理。同步关闭时仍允许清理这些半文件，不清理完整缓存。已经完整上传、等待确认改名的文件进入归档恢复，不按半文件删除。

**开启删除原片后，整组需要归档的素材完整导入缓存即可清理相机，不等 SMB 上传。此时缓存盘可能是唯一副本。** 删除前核对全部成员和身份；需要归档的成员验证完整缓存，已归档且缓存已清理的成员验证正式文件。只有已明确选择忽略且关联未变的预览文件可免于副本核验，它们会随原片联动清理。分段视频、独立音频等仍须整组完成。删除期间保护对应缓存，只调用原有单文件删除接口并复扫。关联不明、身份变化、新增成员或残留附属文件保留并报告。原片删除失败不阻塞上传，未归档完整缓存始终保留。

HERO9 固件 `HD9.01.01.72.00` 已通过短视频实机验证：MP4 与 LRV 完整导入后，删除 MP4 会联动移除对应 LRV，两份缓存随后继续归档。照片、连拍的删除行为仍待专项验收；其他型号或固件当前禁用自动删除，详见[兼容性说明](deployment.md#相机兼容性)。

## 启动自检

传输服务每次启动检查：配置格式、SQLite 数据库、缓存盘挂载与卷身份、一次微小的本地写入、磁盘预留、SMB 认证与目录访问、飞书应用认证。相机未确认时显示等待，确认后可通过 `check` 核对身份及就绪状态。自检不会传输素材、删除原片或发送测试消息。相机离线不妨碍已有完整缓存上传；SMB 离线不妨碍已确认相机导入；数据库损坏会阻止传输。

启动自检结果保存在 SQLite；当前状态随连接情况刷新。需要重新检查时使用命令：

```sh
docker compose exec backup python3 -m media_importer check --json
```

这项检查不冒充完整传输验收：SMB 写入和改名权限、飞书接收人和发送权限，仍以实际传输和通知结果为准。容器无法启动时先运行 `docker compose ps` 和 `docker compose logs --tail 100`，检查 Docker 与宿主机挂载。

## 缓存核验

完整缓存迁移后显示「待核验」时，先停止同步并接回原相机、原存储卡，通过独占维护命令核验：

```sh
docker compose stop backup
docker compose run --rm --no-deps backup verify-cache
docker compose up -d backup
```

核验不会开启同步、上传文件或删除相机原片。旧记录须满足既有完整导入记录、大小和修改时间一致，并核对相机素材身份及最多五段 64 KiB 内容；未通过的原文件和记录保留待处理。不完整读回视频，不计算视频 SHA-256。相机不可用时不会仅凭同名同大小恢复完成数量。

运行中的 SQLite 只通过容器内命令访问；不要用宿主机 SQLite 工具打开正在被 Docker 使用的数据库。离线备份前先停止 Compose。

## 故障排查

```sh
docker compose exec backup python3 -m media_importer status
docker compose exec backup python3 -m media_importer status --json
docker compose exec backup python3 -m media_importer check --json
docker compose exec backup python3 -m media_importer sync off
docker compose exec bot python3 -m media_importer bot-panel
docker compose logs -f --tail 100
docker compose stop
```

SMB 离线只暂停上传；缓存额度或空间不足暂停新导入；缓存盘不可用时两路等待。认证、权限等问题按提示修改 `.env`，重建容器。单个源文件、缓存或待归档文件异常会单独记录，其他可处理文件继续；失败文件不计为完成。文件重试从配置的 `retry_seconds` 起逐步退避，最长一小时，重启后保留重试时间。完整缓存身份不符时原文件始终保留，可停止同步后执行[缓存核验命令](#缓存核验)。

传输失活检测独立于服务心跳：只有正在工作的队列长时间没有成功读写或请求活动才触发，空队列、离线等待、内部锁等待不算失活，低速限流也会延长阈值。默认至少 120 秒，随相机请求超时与上传限速调整。先取消本次尝试并重建连接；取消后 30 秒仍无法退出，服务以退出码 75 结束，由 Compose 重启。未完成临时文件按原规则恢复清理，完整缓存及归档记录保留。

| 部署时的现象 | 处理方式 |
| --- | --- |
| `docker compose` 不存在 / 无法连接 Docker | 安装 Compose 插件或启动 Docker Desktop，确认 `docker compose version` 和 `docker info` 可用 |
| `bind source path does not exist` / 挂载被拒绝 | 确认 `.env` 是文件、三个宿主机目录已存在、外接盘已挂载且 Docker 有目录访问权限 |
| 稳定版镜像下载失败 | 检查 Docker 到 `ghcr.io` 的网络；公共镜像无需登录。若选择源码部署，运行 `python3 scripts/build.py --activate` |
| 外接盘构建报 `failed to xattr ._...` | 使用 `python3 scripts/build.py`，会在临时目录构建，不读取 AppleDouble 元数据 |
| 构建卡在下载基础镜像或依赖 | 检查 Docker 自身的网络/代理、Docker Hub 和依赖源访问，替代构建方式见[构建与测试](#构建与测试) |
| 宿主机可访问相机或 SMB，容器不通 | 检查 Docker 网络与宿主机 VPN 路由；用容器内 `check --json` 验证，不能仅凭 Finder/资源管理器访问成功判断 |
| SMB 域名间歇超时，但 IP 或 VPN 地址正常 | 先区分 DNS 查询、TCP 连接与 SMB 认证。使用 Clash/Mihomo 时，检查域名的 A/AAAA 查询是否超时；可用 [nameserver-policy](https://wiki.metacubex.one/config/dns/#nameserver-policy) 只为该域名指定可靠的 DNS。同一存储更换域名/IP 后会核对既有归档身份，核验通过继续原任务；不再按地址另建目的地 |
| SMB 已认证但目录不可访问 | 核对共享名与相对目录，提前创建子目录；服务器内部路径不能用作共享名 |
| 飞书菜单不显示 / 按钮无回复 | 按 [飞书排障表](feishu.md#常见问题) 分别检查发布、消息订阅、卡片回调与本人 Open ID |

## 目的地身份与恢复

同一数据目录绑定一个逻辑目的地，绑定保存在 SQLite 中。v0.10.10 首次启动沿用原目的地键，不改任务、归档路径或通知标识；`.env` 与 `settings.json` 无需改格式。修改主机、端口、账号、共享名或目录后，先核对原有正式文件的大小和 SMB 文件身份，确认仍是同一归档后才允许上传或清理远端临时文件。核验只读取元数据，不下载视频。

无法确认时保留任务与完整缓存，并提示“目的地身份待核对”。只有完全没有远端操作记录的目的地可以直接纠正连接；存在尚未确认的发布、但没有正式归档可核对时，请先恢复原连接完成恢复。真正更换存储应使用独立的数据目录和缓存目录，不手工改数据库强行接管旧任务。

删除事实与源文件当前缺失分开记录：新的确认删除保留时间，复扫不会把“已删除”改成“原片不存在”；旧记录如果已是 `absent`，不会推测成程序删除。缓存成功清理会留下完成记录，后续轮次不再反复删除和写回。同一未变文件的状态查询最多复用 30 秒的抽样结果；文件元数据、卷或凭据变化立即重新核验，上传和删除前始终重新核验。

后台关键线程意外退出会重建；连续三次失败则退出服务，由 Compose 的重启策略恢复。通知线程单独重试，不因此中断传输。相机或 SMB 离线仍按原规则等待，不因此重启容器。Docker 健康检查只读服务心跳、线程与传输活动状态，不扫描视频缓存。

## 完整缓存恢复

v0.10.11 起，完整缓存附带 `.receipts/` 恢复清单，保存素材身份、原文件名、目的地、抽样凭据和远端发布依据。清单成功落盘后才允许删除相机原片；归档及缓存清理成功后对应清单一起移除。升级会为核验通过的既有完整缓存补齐清单，不重传或改名已有归档。

后台每五分钟保存一次 SQLite 一致快照到数据目录的 `recovery/`，保留最近三份；任务收尾后，成功生成新快照再淘汰旧快照。手动备份及升级回滚备份不自动删除。`status --json` 的 `metadata_backup` 显示最近结果。快照保留未完成事项和去重索引，但不复制视频或 `.env`；完整迁移使用[备份与迁移](#备份与迁移)。

数据库不可用时，先停止两个服务。以下命令只读取原缓存，输出到数据目录下的**新目录**，不替换原数据库，也不上传或删除素材：

```sh
docker compose stop
docker compose run --rm --no-deps backup recover-cache --output /data/recovered-YYYYMMDD
```

查看生成的 `recovery-report.json`。通过核验的完整缓存恢复为原任务 ID、归档路径及发布依据；不能确认的文件列入 `rejected` 并保留。恢复后的同步与删除原片均关闭，远端发布结果会再次核对，不能只凭同名同大小认领。恢复只用于未完成事项，不从归档目录推断历史任务。

准备启用恢复结果时，在原项目 `.env` 中将 `MEDIA_IMPORTER_DATA_HOST_DIR` 指向新目录的 `data`，`MEDIA_IMPORTER_CONFIG_HOST_DIR` 指向新目录的 `config`，`MEDIA_IMPORTER_CACHE_HOST_DIR` **仍指向原缓存目录**；其他连接与凭据保留。填写宿主机绝对路径，然后 `docker compose up -d --no-build`，核对状态后再开启同步。不要同时运行原实例与恢复实例。

只需取出文件时，可以改用下列命令，把通过核验的完整缓存复制为「设备目录／原文件名」，同名加后缀；原缓存不动，输出目录需有足够空间：

```sh
docker compose run --rm --no-deps backup export-cache --output /data/exported-YYYYMMDD
```

恢复依赖原缓存卷标识、完整文件和对应清单；迁移时三者一起保留。没有有效清单的文件不会按大小或文件名自动接管。恢复核验只读取少量内容抽样，不计算视频全量 SHA-256，也不读回远端视频。

## 日常升级

在 Git 克隆的项目目录执行以下命令（需要 Python 3.9+、Git、Docker Compose；Windows 将 `python3` 换成 `py -3`）：

```sh
python3 scripts/manage.py update
# 可指定已发布的稳定版本；不允许倒退或覆盖本地源码改动：
python3 scripts/manage.py update --version 0.10.19
```

命令只读取 GitHub 正式发行版，核对发布清单、Git 标签和镜像版本，按摘要下载 ARM64/AMD64 镜像，再停止两个服务、保存一致性快照、快进源码、恢复原来运行的服务并等待健康检查。原来停止的服务保持停止；`.env`、JSON 开关、未完成任务和完整缓存保留，SMB 归档不改动。未完成的单文件传输遵循现有规则，下次从头传输；完整文件不重传。相机连接在重启后重新确认。

下载失败不停止服务。停止后若检查或启动失败，命令退出并尽量保持两个服务停止，打印恢复资料路径；不会自动覆盖可能已更新的数据库。快照位于 `backups/update-*/`，包含数据库、连接凭据、JSON、旧源码和镜像身份，**不复制视频，也不代替完整迁移备份**。排除网络或凭据问题后可以重试；若涉及数据版本回滚，应先停止服务并按快照记录检查当前任务，不能直接用旧数据库覆盖新记录。

更新工具拒绝本地源码改动、分叉提交、自定义 Compose 覆盖文件或不支持的数据版本。连接与缓存挂载缺失时不会创建替代目录。`compose.override.yaml` 用于本机镜像固定，保留但不提交；删除它会回到 `compose.yaml` 指定版本。

v0.10.15 及更早版本尚无此命令，首次先执行 `git pull --ff-only` 获取管理脚本，再执行上述更新命令，不运行配置向导、不覆盖配置。备份恢复目录未携带 `.git`，继续使用离线恢复方式；统一更新暂限 Git 克隆安装。飞书菜单与权限仍由应用后台维护，本次无需重新发布。

## 备份与迁移

宿主机需要 Python 3.9+ 和 Docker Compose。执行一条命令，自动暂停两个服务、保存 SQLite 一致快照、配置、连接凭据、程序与所有缓存，核验后恢复原来正在运行的服务。原配置和缓存不变。备份目录包含明文凭据，请私下保管；默认不压缩视频，也不计算视频全量 SHA-256。配置和数据库使用校验和，媒体沿用大小、修改时间与少量内容抽样核验。

在项目目录执行，`--output` 必须指向新目录。建议选外接盘，不能放在当前缓存目录内：

```sh
python3 scripts/manage.py backup --output "/Volumes/MediaSSD/media-importer-backups/backup-YYYYMMDD"
```

备份完整缓存需要对应的可用空间。仅有 `manifest.json` 且核验通过的目录才是完成的备份；中断会留下 `.incomplete-*` 目录并恢复原服务，该目录不能用于恢复。外接盘同盘备份可用于迁移和回滚；需要防止整块盘损坏时，应把完成的备份复制到另一块磁盘。

将**整个备份目录**复制到新电脑。恢复只接受尚不存在的项目目录与缓存目录，避免覆盖现有资料；两者应相互独立。可直接使用备份内携带的脚本：

```sh
python3 "/path/to/backup/project/scripts/manage.py" restore \
  --from "/path/to/backup" \
  --project "/path/to/media-importer" \
  --cache "/path/to/media-cache"
```

脚本准备相应版本镜像（本机没有时从备份源代码构建，需要联网）、核验并复制配置、记录和缓存、调整 `.env` 三个挂载路径。其他连接参数与归档记录保持不变。恢复后的同步与删除原片强制关闭，旧控制卡和待执行命令失效，历史待发通知取消，**不自动启动服务**。完整缓存保留原修改时间和卷标识，继续按既有任务归档。

停止旧电脑的两个 Compose 服务，再进入新项目目录运行 `docker compose up -d`，查看启动自检与飞书状态后开启同步。相机连接由新版重新发现并在飞书确认；可在 `.env` 的 `SOURCE_URL` 提供优先探测地址。不要同时运行指向同一目的地和同一飞书应用的两套实例。Windows 可使用 `D:/MediaImport/app`、`E:/MediaImport/cache` 等路径；实际 Windows 相机链路仍需实机验收。

## 从 v0.9 升级

先停止两个服务并备份旧源代码、镜像、`.env`、配置、数据目录与缓存清单。完整缓存保留在原盘，不要清空。

```sh
docker compose stop
python3 scripts/build.py --activate
docker compose run --rm -T --entrypoint python3 backup /app/migrate_v010.py
docker compose up -d --no-build
```

迁移必须在 Docker 内、原缓存挂载可用时进行。脚本先保存 SQLite 完整快照、旧 JSON 与 `.env` 到 `data/pre-v0.10.0-*`，再执行一次性 v3/v4 → v4/v5 升级。保留目的地身份、任务 ID、归档路径、完整缓存与历史记录；旧半文件登记待清理，取消旧控制请求和待发通知，不补发历史完成提醒。升级后同步和删除原片关闭，其他有效设置保留。

只支持由 v0.9 迁移，不提供旧配置的运行时兼容。回滚先停止新版，再使用备份恢复对应版本的源代码、镜像、配置及数据；已清理的半文件无法恢复字节进度，旧版需重新确认并重传该文件。不要在新版已经归档或删除源素材后直接覆盖回旧数据库。

迁移电脑时复制 `.env`、配置、数据以及所有未归档完整缓存，保留缓存卷标识；修改宿主机挂载路径。新缓存凭据绑定素材、缓存卷、大小、修改时间和最多 320 KiB 内容抽样，容器重建导致的 inode 变化不会使已完成数量归零。抽样用于身份核验，不是全文件内容校验。迁移时需保留修改时间和缓存卷标识；不匹配的完整缓存保留并显示待核验，绝不覆盖重下。

## 构建与测试

普通部署直接下载稳定版镜像。开发时运行 `python3 scripts/build.py --activate` 构建本机镜像并写入本机 Compose 覆盖文件，然后使用 `docker compose up -d --no-build --pull never`；该步骤不发布镜像。需要 ARM64、AMD64 两种本机镜像时可执行 `python3 scripts/build_images.py --arch all`，跨架构构建需 Docker 提供相应模拟能力。源码构建需要访问 Alpine、Python 包源及基础镜像仓库；构建上下文只包含程序和依赖。

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -s tests
```

GitHub Actions 在推送和 PR 时运行 Python 3.11/3.14 回归测试、源码文件检查和 Docker 构建；不连接相机、SMB 或飞书。`python3 scripts/check_repository.py` 检查受跟踪文件中的运行数据和明显凭据特征，但不能替代人工复核。

维护者发布匹配程序版本的 `vX.Y.Z` 标签后，`Stable release` 工作流先运行测试，再构建并验证两种架构，发布版本镜像、`stable` 别名和包含镜像摘要的 `release.json`。镜像使用 Actions 的内置 `GITHUB_TOKEN`，无需在仓库保存镜像仓库密码。首次创建 GHCR 包后需在包设置中确认公开可见，并验证匿名拉取；正式发布不使用个人 `.env`、数据或缓存。

单元测试使用临时目录、小文件和模拟设备，不需要真实凭据。实机验收请使用独立的 SMB 测试目录和可删除的小文件。

## 仓库与本机数据

仓库只包含源码、测试、部署文件和配置示例。真实 `.env`、`config/settings.json`、SQLite、完整缓存、备份包和运行日志均不提交。首次安装从示例创建本机配置；迁移既有实例使用完整备份与恢复命令，单独克隆仓库不包含任务记录或未上传的素材。

如果将挂载目录改为仓库内的其他位置，先将该目录加入 `.gitignore`；默认忽略规则只覆盖约定的本机目录。提交前用 `git diff --cached --name-only` 核对文件，不用 `git add -f` 强制加入本机配置。`.dockerignore` 仅允许构建所需源码与依赖清单进入镜像，并排除 macOS 元数据文件。
